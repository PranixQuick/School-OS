| BUG-004 | 2026-08-05 | Claude (Wave 12 Release Certification, via Supabase security advisor) | Critical | Any unauthenticated request to `/rest/v1/rpc/safe_select` with `{"p_query": "<any SQL>"}` — e.g. `SELECT * FROM students` for any school. | `public.safe_select(p_query text)` is a `SECURITY DEFINER` function that runs `EXECUTE format('SELECT jsonb_agg(t) FROM (%s LIMIT 1000) t', p_query)` — i.e. executes caller-supplied SQL verbatim. It carried `EXECUTE` grants for `anon` and `authenticated` (plus the default `PUBLIC` grant every Postgres function gets unless explicitly revoked), making it callable by any unauthenticated caller with the project's public anon key via PostgREST's `/rpc/` endpoint — bypassing this app's own custom-cookie auth entirely and, being `SECURITY DEFINER`, very likely bypassing RLS/tenant isolation on whatever table was queried. | None (database grants only, no application code touched) | Found via Supabase's built-in security advisor (`get_advisors`, type=security) during Wave 12 checks. Confirmed via direct query of `information_schema.routine_privileges` that `PUBLIC`, `anon`, and `authenticated` all held `EXECUTE`. Fix applied directly to production (founder-authorized) via `REVOKE EXECUTE ... FROM PUBLIC/anon/authenticated`, keeping only `postgres` and `service_role`. Re-verified via two independent read paths (Pranix gateway + personal Supabase connector) post-fix: only `postgres` and `service_role` retain `EXECUTE`. Confirmed no app code calls this function through the public API (app only ever uses the service-role client), so nothing in the app depends on the revoked access. | Fixed | Applied directly to production; no PR/migration file exists for this yet — a follow-up migration file documenting this grant change should be added to `supabase/migrations/` for history-consistency, same rationale as the BUG-001/BUG-003 corrections above. |
